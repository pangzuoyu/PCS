## 1. 增补说明

### 1.1 增补目的

消解原规格体系中"签署与版本作用对象"的根本矛盾：P0 Schema 给每条业务记录配 version + sign_status，而 SUP-004/005 的签署页与版本目的是按交付物（文档）发布的工程实践。本增补确立**两层签署模型**，重构记录层状态机、变更管理、血缘锚定、设备表同步、交付物编号与客户签署机制，并对齐演示版许可计数口径。

### 1.2 核心变更概述

| 维度 | 原方案 | 新方案 |
|---|---|---|
| 签署对象 | 每条记录走四级签署并各自版本化 | 两层：记录层数据门禁（9 态、无 Rev）；交付物层独占 Rev/版本目的/签署矩阵 |
| 记录层状态 | DRAFT~APPROVED 固定 10 态 | DRAFT / IN_APPROVAL / CHECKED / CHECK_REJECTED / STALE / CHANGE_PENDING / CHANGED / REVERSAL_PENDING / OBSOLETE，批准深度可配置 1~4 级 |
| 已发布记录修改 | 作废重建（OBSOLETE+新记录） | CHANGE_PENDING→CHANGED→凭证关闭（变更单或新版交付物），哈希判定实质变更 |
| 上游变更回退 | 状态回 DRAFT / 作废重建 | STALE+哈希判定：结果不变自动恢复，结果变走变更流程 |
| 版本历史 | xxx_History 快照流水表 | 三处承载：变更前快照（回滚）/ 交付物版本（发布固化）/ 审计日志（行为） |
| 血缘锚定 | record_id + version | record_id + record_hash，附 formula_version / config_version |
| 变更单 | 无 | 交付物子类型（CHANGE_NOTICE），复用一套状态机/编号/历史 |
| 客户签署 | 预留外部链接 | v1 凭证代录（附件+二次认证+审计区分） |
| 设备表同步 | 计算保存即同步 | CHECKED 触发同步 + 状态联动；哈希只盖设计参数 |
| 位号 | 未定义弃用后行为 | 终身唯一，弃用不复用 |
| 演示版计数 | "每模块 3 条"口径未定 | 活记录计数（非 OBSOLETE），弃用返还配额 |

## 2. 两层签署模型（ADR-0001）

| 层级 | 对象 | Rev | 签署状态 | 签署机制 | 版本目的 |
|---|---|---|---|---|---|
| 记录层 | 每条计算记录（1 条管道、1 台泵） | ❌ | ✅ 9 态门禁 | record_approval_config（1~4 级深度） | ❌ |
| 交付物层 | 文档（管道一览表、计算书、变更单） | ✅ A/B/0/1/AS-BUILT | ✅ 发布状态 | signature_matrices（SUP-005） | ✅ |

记录层确认"单条数据正确"；交付物层确认"整份文档可发布"。两层深度相互独立，记录层深度 ≤ 交付物层深度为常规配置。

## 3. 记录层状态机（ADR-0002/0003/0009/0010/0012）

### 3.1 状态定义（RecordSignStatus，9 值）

| 状态 | 含义 | 可编辑 | 可被交付物绑定 |
|---|---|---|---|
| DRAFT | 草稿（含试算数据） | ✅ | ❌ |
| IN_APPROVAL | 批准流程进行中（复合状态，approval_step/depth/role 追踪） | ❌ | ❌ |
| CHECKED | 该记录类型配置的全部批准步骤通过（数据正确性完整确认） | ❌ | ✅ 唯一准入 |
| CHECK_REJECTED | 某批准步骤退回 | ✅ | ❌ |
| STALE | 已绑定记录被上游变更波及，数据存疑（只读） | ❌ | ❌ |
| CHANGE_PENDING | 变更中（修改+重新批准） | ✅ | ❌ |
| CHANGED | 已变更，等待关闭凭证 | ❌ | ❌ |
| REVERSAL_PENDING | 撤销 CHANGED 的审批中 | ❌ | ❌ |
| OBSOLETE | 人工弃用终点 | ❌ | ❌ |

### 3.2 批准深度（record_approval_config）

按记录类型在项目模板配置，1~4 级（可含 CUSTOMER 步骤，走凭证代录）。典型：PSV 4 级、PUMP/HEAT 3 级、PIPE/VESSEL/CV 2 级、FLASH 中间计算 1 级。设备记录从来源计算记录继承批准深度。

### 3.3 实质变更 = 结果哈希变化

record_hash = SHA-256(计算结果字段，数值规范化舍入 6 位有效数字后)，不含元数据与商务字段。上游数据变动但重算哈希不变 → 无变更、无凭证。

### 3.4 关键路径

- **主动修改**：CHECKED(锁定) → 发起变更申请 → CHANGE_PENDING → 重新批准 → CHANGED → 凭证关闭 → CHECKED
- **上游变更**：锁定记录 → STALE（自动存变更前快照）→ 确认重算 → 哈希不变恢复 CHECKED / 哈希变化 → CHANGE_PENDING → …；未绑定记录直接回 DRAFT 重算
- **撤销（以"是否已对外生效"为界）**：CHANGE_PENDING 设计人自行放弃；CHANGED 经 REVERSAL_PENDING 由撤销批准链批准（3 级矩阵取 REVIEWER、4 级取 APPROVER）；已凭生效的变更只能发起反向新变更（CHANGE_REVERSAL）
- **弃用**：未绑定免凭证直接 OBSOLETE；已绑定须走变更单（change_type=RECORD_CANCELLATION）。**位号终身唯一**：唯一约束 (project_id, tag_number/line_no) 覆盖含 OBSOLETE 全部记录，弃用不释放、永不复用，替代分配新号

## 4. 变更管理（ADR-0002/0008）

变更单 = deliverables 表中 deliverable_type=CHANGE_NOTICE 的一行；签署、编号（编号模板映射 PR/KDC）、Rev、快照全复用交付物机制；特有字段（change_type/reason/triggered_by）在 1:1 扩展表 change_notice_details。默认 3 级矩阵、版本目的 ISSUED_FOR_CHANGE。APPROVED 后系统自动将绑定记录 CHANGED → CHECKED 并写入 change_resolved_by。change_type 枚举：DATA_CORRECTION / PROCESS_CHANGE / UPSTREAM_CHANGE / CLIENT_COMMENT / RECORD_CANCELLATION / CHANGE_REVERSAL / OTHER。

## 5. 交付物层

### 5.1 数据模型

新增表：deliverables（含 deliverable_type、scope_type/scope_value 拆分范围、doc_no、current_rev、version_purpose、sign_status、matrix_id、客户批准字段组）；deliverable_versions（rev、record_snapshot、signature_summary、pdf 路径）；deliverable_record_bindings（record_id + record_hash + old_record_hash_before_change）。

### 5.2 绑定与发布规则（ADR-0001/0012）

仅 CHECKED 记录可绑定（其余 8 态一律拒绝，整份拒发）。发布时快照固化；被绑定记录锁定；快照与当前哈希不一致的 Rev 标记 AFFECTED（商务字段变更不触发，PURCHASE_LIST 类交付物发布时对商务字段整体快照）。

### 5.3 编号模板（ADR-0006）

doc_no 由项目模板级编号模板生成：段类型 PROJECT_FIELD / DELIVERABLE_FIELD / SEQUENCE / FIXED / MANUAL / DATE + 分隔符 + 类型映射；SEQUENCE 按 scope 原子分配、不回收、可跳号。同类型可按装置拆分多份，各自独立 Rev。新增表 numbering_templates、doc_no_sequences。

### 5.4 客户批准 = 凭证代录（ADR-0007）

客户在系统外批准（邮件/信函/EDMS/签字文件），项目负责人/文控/审定代录：凭证附件（必填、SHA-256 防篡改）+ 客户姓名 + 日期 + 方式 + 代录人二次认证；审计 CUSTOMER_APPROVAL_PROXIED，签署页显示"客户姓名（代录：X）"；代录人不得为该交付物设计人。CUSTOMER 步骤状态：CUSTOMER_PENDING → CUSTOMER_PROXIED / CUSTOMER_REJECTED（代录退回）。v2 演进外部链接。

## 6. 设备表集成（ADR-0005）

来源计算记录 CHECKED 时自动创建/更新设备记录（DRAFT 不进设备表）；来源状态变化联动传导（STALE/CHANGE_PENDING/CHANGED/关闭）。设备记录哈希仅覆盖 tag_number + type_code + design_parameters_json + source_module + source_record_id；商务/采购/图纸/交付/安装/重量字段直接编辑、不进门禁。设备记录 CHANGED 关闭凭证三选一：来源关闭连带、自身变更单、设备一览表升 Rev。EQUIP_LIST / EQUIP_DATASHEET / PURCHASE_LIST 为交付物类型。来源记录 OBSOLETE → 设备记录 sign_status 跟随、EquipmentStatus=D。

## 7. 工作区与物流（ADR-0004/0014）

门禁、交付物、变更单仅存在于 FORMAL 工作区；PERSONAL/TEMPORARY 记录永远 DRAFT（试算），可只读快照引用正式区 CHECKED 数据（不自动同步、不参与 CIA）；导入正式区 = 新 record_id 从 DRAFT 重走门禁，原记录保留并标记已导入。

物流（streams）采用独立简化状态集 StreamSignStatus = DRAFT / IN_APPROVAL / CHECKED / OBSOLETE：初次导入须校对（来源一致性、组成归一化 100±0.5%、单位、完整性；深度 1~2 级可配），DRAFT 不可被计算记录引用；CHECKED 后修改不重校对——限权（DESIGNER+项目负责人）+ 强制原因 + 影响预览，状态保持 CHECKED 并触发 CIA。

## 8. 血缘与历史（ADR-0013）

data_lineage 删除 source_version/target_version，改为 source_record_hash / target_record_hash，保留 formula_version、新增 config_version；只追加。CIA = 变更记录新哈希 vs 血缘哈希不匹配定位下游（级联在下游重算时逐级传播，不预递归）。删除全部 xxx_History 表；历史三处承载：record_change_snapshots（进 STALE/CHANGE_PENDING 前写、撤销/放弃时回滚）、deliverable_versions+bindings（发布固化，仅哈希）、audit_logs（行为流水）。

## 9. 演示版对齐（ADR-0011）

模块配额按活记录计数（sign_status ≠ OBSOLETE），弃用返还配额，可"创建→弃用→再创建"循环。交付物与变更单不限量；报表定义独立限 3（维持 SUP-006）；设备表跟随来源模块活记录。v1 许可仅 FULL/DEMO（TRIAL 枚举预留不实现）。
