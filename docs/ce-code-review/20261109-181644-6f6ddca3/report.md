Response needed: make the missing-record branch raise the same 404 as the no-access branch, correct the comment, and extend `tests/api/v1/test_lineage_guard.py::test_lineage_cross_project_looks_identical_to_missing` to all three suffixes (it currently covers `/graph` only). The check verdicts are therefore dropped and the endpoint can only ever return the submit row. The failure is silent (200 plus a partial list), so a designer never sees the pass or reject verdict -- the whole content TODO-112 exists to deliver. The new test hides it: `tests/api/v1/test_stream_review_log.py:95` fabricates `action="RECORD_TRANSITION"` for all three transitions, a shape production never writes, so the suite is green on impossible data; the frontend MSW mock fabricates the same impossible `PASS_CHECK` row. Response needed: derive the action filter from `TRANSITION_AUDIT_ACTION` (or drop the `action` predicate and keep the `detail_json.transition` filter, which already selects exactly the three transitions), rebuild the test fixture from the real writer's shape, and assert that a pass and a reject row actually appear. How sure: 100, nine reviewers; confirmed by the validator, and reproduced independently by the dispatch context's standalone probe (four real audit rows written, one item returned, the two verdict rows dropped).
- **#3** -- The new guard runs a DB query while the `SELECT ... FOR UPDATE` lock from `stream_batch_service.py:260` is still held, and `_submit_one`'s blanket `except Exception` (`:167-175`) turns a DB-level failure into an `INTERNAL_ERROR` item with no rollback -- unlike the transition path, which rolls back at `:363`. Precondition: a DB-level error during the guard's SELECT. How sure: 75, one reviewer; confirmed by the validator with incidence explicitly not measured.

- **#5** -- In dev / MSW mode the review-log handler returns the same two inline rows for every `stream_id`, including a `PASS_CHECK` row the real backend cannot produce, and never returns the empty-list or 404 shape the endpoint defines. Nothing binds the mock to `components['schemas']['ReviewLogItem']`, so a contract change leaves `tsc` green while dev serves the old shape. This is also why the batch's browser QA reported a 200 with two rows for data the real endpoint never returns, and the backend filter bug (#2) survived it. How sure: 100, two reviewers; confirmed by the validator (read-only inspection, incidence not measured).
- **#9** -- The project guard runs after `select_stream_for_update`, so a caller with access to project A only can hold a `FOR UPDATE` lock on a stream row that belongs to project B until the lock is released at `:290`. This is a lock-ordering side channel rather than a data leak, but it lets one caller briefly block another project's writer. Response needed: the same restructuring as #3 -- a non-locking read of the owning project, the access check, then the locking read. How sure: 75, one reviewer; confirmed by the validator.
- **#10** -- `ensure_user_row` falls back from a `user_id` lookup to a `username` lookup and returns the username-matched row without checking that its `user_id` matches the requested one; `create_project` then grants `PROJECT_LEAD` to `creator.user_id`. For a legacy `users` row whose id differs from the derived id (the case the helper's own docstring says exists), the grant lands on an identity the requester's token does not carry: the creator gets 404 on the project it just created, and an unrelated account is granted access to it. The seed script has the same shape. Response needed (decision): make the substitution explicit instead of silent -- return a mismatch flag or raise, and key the grant on the caller's own identity; if a legacy row must keep its id, register the row migration as a TODO instead of silently redirecting the grant. Which id is authoritative is a policy choice. How sure: 75, four reviewers; confirmed by the validator with incidence not measured.
- **#11** -- `ensure_user_row` does SELECT-by-id, SELECT-by-username, then `session.add` + `flush` with no savepoint, no `IntegrityError` recovery and no re-read of the winner, on `users.username` which is unique. Because mock login never persists a `users` row, two concurrent `POST /projects` by the same user (double click, form resubmit) both see "no row" and both INSERT; the loser hits the unique constraint with an uncaught `IntegrityError`, and because the project INSERT is in the same transaction the whole project creation rolls back. The same shape exists in `grant_project_access`, which is pre-existing but newly reachable from `create_project`. Response needed: the repository's recorded recipe -- `async with db.begin_nested():` around the insert, and on `IntegrityError` re-read the winner and return it read-only, re-raising if the violated constraint is not the expected one. Do not use a bare `db.rollback()` for the recovery. How sure: 75, one reviewer; confirmed by the validator with incidence not measured.
- **#12** -- The guard test file states its own principle ("only 404 tests would also pass if the guard always 404s, so every endpoint needs an in-project control"), but positive controls exist only for `GET /streams/{id}`, `GET /state-points/{id}` and `GET /streams/{id}/state-points`. `PATCH`/`DELETE /streams/{id}`, `POST /streams/{id}/state-points`, the properties reads, the properties estimate and the six transition endpoints have only cross-project 404 assertions, so a guard that rejected the owner's own rows would ship with a green suite. The shared helpers are positively covered through those three controls, so the residual gap is per-endpoint wiring rather than an unguarded helper. Response needed: a parametrized positive-control test over the same endpoint table as the negative one, reusing the `two_projects` / `make_stream` fixtures and the existing role fixtures so the control and the negative case differ only in the grant. How sure: 75, one reviewer; confirmed by the validator.
