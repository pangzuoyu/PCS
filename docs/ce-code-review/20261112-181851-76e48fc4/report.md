- **#1** -- `_delete_own_rows` deletes `users` rows by the name-derived id (`uuid5(NAMESPACE_DNS, username)`), which is the same id a real LDAP login uses, so `--reset` on a dev database wipes a real account's `roles`, `status` and `token_version` and cascades away its `user_projects` grants; when the row disappears, the next login recreates it `ACTIVE`, so a deliberately disabled account is silently re-enabled. The script's own contract says `--reset` only deletes rows it created, and the batch's must-not-regress rule 6 says the same. Response: restrict the reset delete to rows this script created (a seed-specific marker, or drop the `delete(User)` entirely since `_ensure_users` is already idempotent) and preserve an existing row's `status` and `roles`; make `test_reset_only_deletes_our_own_rows` table-driven over User, Stream, Project and UserProject. Confirmed independently by three reviewers (data-loss).
- **#3** -- the middleware sits outside routing, hence outside authentication, so any anonymous client can make the worker hold its body in RAM before a credential is checked; the per-request cost is roughly twice the body (the chunk list plus the joined copy), the 10 MB cap is per request with no aggregate bound, and no legitimate AI payload is anywhere near that size. Response: lower the cap to a settings-backed value sized for the AI schemas, buffer into one `bytearray`, and return 413 on an oversized `content-length` before reading. Confirmed, but the number of concurrent uploads needed to exhaust a worker was not measured (memory-safety).
- **#4** -- the EMAIL rule is an unanchored greedy `X+@...` pattern, so on a body with no `@` the engine re-tries the tail at every start offset; `_sanitize_text` is plain synchronous code called with no `await` point from the async middleware, so the cost lands on the event-loop thread. **The quadratic cost is now measured** through the production function `hash_sanitized`: 40 KB -> 1 107 ms, 80 KB -> 4 245 ms, 160 KB -> 17.0 s, 320 KB -> 68.1 s, against a control body containing `@` at 80 KB -> 1.5 ms (size x2 gives time x4). Every one of those sizes sits inside the 1 MiB hashing window (`MAX_HASH_BYTES`), so one unauthenticated 320 KB POST to `/api/v1/ai/*` pins the event loop for 68 s and, on a single-worker uvicorn, stalls every endpoint of the service. Two corrections from the validation batch: the hash runs in the middleware's `finally` **after** the response, not before authentication (the exploitability is unchanged because a row is written on every outcome and the 5/min per-IP limiter only changes the status code), and the hashing surface is **wider** than first stated, because the prefix test runs before routing, so any `/api/v1/ai/<anything>` path -- even an unrouted one -- has its body read and hashed (see #29). Response: bound the greedy quantifiers to the RFC 5321 limits so the scan is linear, and cap the characters scanned per string. A re-grade to P0 was proposed and **refused by the independent validator** (impact is availability-only: CVSS AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H = 7.5; the sibling pre-auth resource findings on this same path, #3 and #18, are graded P1), so it stays P1 and heads the fix queue.
- **#5** -- **dropped by the independent validator, not a live finding.** The cited code holds against the reviewed revision: `app/services/ai/arq_queue.py:67-69` logs a warning per failed enqueue and the module docstring states the deliberate "failure degrades, never raises" policy, so the proposed fix (a counter plus an `audit_pipeline` field on `HealthAIResponse`) is new observability rather than a repair of anything the code contradicts. The number is kept so the 1-29 sequence has no gap; the substance is carried as a residual risk and as part of #16 and #21. The external reviewer reached the same verdict independently.
- **#6** -- the task swallows every write exception and returns normally, so ARQ records the job as successful and deletes it: no retry (arq 0.28 retries only `Retry`, as this repo's own `report_tasks.py:212-214` demonstrates), no dead letter, and the row never appears, while the request already returned 501. `worker.py:237`'s `max_tries = 3` is unreachable because the exception never escapes the task. Response: replicate the bounded retry already used by `report_tasks.generate_report_task` (read `job_try`, raise `Retry(defer=RETRY_DEFER_S)` up to `MAX_TRIES`), keep the `IntegrityError` branch as idempotent success, and add a test that injects one write failure. Confirmed (data-loss).
- **#7** -- the guard detects SDK imports of a fixed name list and `httpx` calls whose URL literal contains one of four markers; the natural bypass, `httpx.post("http://llm.internal:8000/v1/chat/completions", ...)`, matches neither rule and stays green, so the call-time CIDR re-check, the sanitizer and the audit callback are bypassed with no red. The SDK half is vacuous today because those packages are not installed. Response: invert the rule (deny network-client imports and client constructions outside `core/outbound_ai_client.py`), keep the URL-marker rule as an extra signal, and add a negative control so the scanner is observed failing at least once. **Wording corrected in round 2:** the batch ledger records a *manual* negative control (a probe with `import openai` plus an `httpx` call to `/api/v1/ai` made both rules red), so "the guard has never been seen red" was inaccurate; what is true is that **no negative control ships with the repository**. Confirmed (must-not-regress rule 7 is not met).
- **#8** -- the smoke asserts only login, a dashboard heading and an empty console error list; mock-login never creates a `users` row, `/auth/me` allows a missing row, and the axios interceptor only reacts to 401, so a backend answering 404 for every project-scoped endpoint produces no console error and the shell still renders. The seeded `UserProject` grants never reach the database under test, because the documented start-up command sets no `DATABASE_URL` and therefore reads the dev `pcs` database while the seed writes `pcs_pgtest`. Response: point the E2E backend at the seeded database and replace the shell-level assertion with a data-level one (a project-scoped GET returns 200 and the seeded rows are visible). Confirmed, with one half of the concern partly mitigated: the channel itself does start 5174 with `VITE_ENABLE_MOCK=false` and `reuseExistingServer: false`, so MSW is off in that channel; the confirmed defect is the database mismatch plus the missing data-level assertion.
