- **#1** -- `load_record` applies `.with_for_update()` and both write paths pass `for_update=True` (`submit_approval` at `records_actions.py:424`, `approval_step` at `:531`), and the in-code comments state the guarantee as fact ("concurrent submit must be one-wins-one-rejects", "exactly one `APPROVAL_STEP_PASSED` audit row"). Nothing observes it. The unit suite runs on in-memory SQLite, where SQLAlchemy compiles `with_for_update()` to an empty string (no lock at all). The test that is supposed to cover this, `test_second_submit_after_commit_is_409`, is serial by construction and its own docstring (`test_record_approval_chain.py:441-446`) hands the PG verification to the "CI fresh-PG api-drift job" -- but the only workflow in this repo (`.github/workflows/check-api-drift.yml`) runs `alembic upgrade head`, the OpenAPI export and drift check, `check_migration_idempotency.py`, one visual-renderer test file and the frontend typecheck; it never runs the backend API suite and never issues a concurrent request. The repo's own escape hatch for this class of test (`# [->E2E] test_doc_no_unique_under_concurrent_issue`, `tests/api/v1/test_deliverable_issue.py:429`) is likewise a tombstone comment with no test behind it. Consequence: deleting `.with_for_update()` leaves the whole suite green, and on a real PostgreSQL two concurrent submits would both return 200, the second overwriting the first's frozen chain and writing a duplicate audit row -- precisely the harm the comment claims the lock prevents. Fix: (1) add a dialect-level test that needs no PostgreSQL server -- compile the locking SELECT against the PostgreSQL dialect and assert the emitted SQL contains `FOR UPDATE`; (2) correct the false delegation in `test_record_approval_chain.py:441-446` to point at a test that actually exists; (3) if a real two-connection test is wanted, model it on the isolated-schema subprocess harness in `tests/alembic/test_p9_013_bind_default_record_matrix.py`. Validator verdict: **confirmed** (protected subject: concurrency). The validator recorded that the lock itself is real but that the incidence of a concurrent request was never measured -- no such test exists to run. Severity P1 stands.
