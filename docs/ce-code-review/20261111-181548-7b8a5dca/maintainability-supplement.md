## M1 [P2 · conf 75 · manual/human] Guard registry derived from RECORD_TYPE_REGISTRY omits PsvResult  ← **重复**：与已验证的主 finding #8 同源
- **位置**: pcs-backend/app/services/lineage_registry.py:59  ·  pre_existing=False
- **Why**: The guard registry is derived from RECORD_TYPE_REGISTRY, but that registry is not the set of models that actually write data_lineage rows — PsvResult writes lineage rows (psv_persist.py:444 -> finalize_calc_record -> LineageTracker.track -> record_type = record.__class__.__name__ == 'PsvResult') and the PSV API already queries exactly that value (app/api/v1/psv.py:247 DataLineage.record_type == 'PsvResult'), yet PsvResult has zero occurrences in calc_lineage.py, so it never enters LINEAGE_GUARDED_RECORD_TYPES. The 'derived, never hand-copied' promise therefore buys completeness only relative to a registry whose scope is ADR-0031 (result tables with record_hash), not relative to 'types that own lineage rows'. Consequences: (a) GET /lineage/PsvResult/{id}/{upstream,downstream,graph} is permanently 404 even though those rows exist — a silent, undocumented hole in a newly fail-closed endpoint; (b) the next finalize_calc_record caller that is not in RECORD_TYPE_REGISTRY falls out the same way, with no test to catch it. The set that matters is the set of lineage writers, so that is the set the guard should be derived from.
- **Fix**: Stop deriving the guard from a registry whose scope is 'editable result tables'. Either (a) add PsvResult to RECORD_TYPE_REGISTRY (it is a project-scoped model with a record_hash column, so it qualifies), or (b) better: derive LINEAGE_GUARDED_RECORD_TYPES from the actual lineage-writer set — e.g. an explicit LINEAGE_WRITER_MODELS tuple that finalize_calc_record's callers must be drawn from — and add a contract test asserting every model passed to finalize_calc_record appears in LINEAGE_GUARDED_RECORD_TYPES (mirroring tests/architecture/test_record_type_vocabulary.py's role for edit_guard). Option (b) removes the hidden coupling between 'can be edited' and 'has lineage' that produced the hole.

## M2 [P2 · conf 100 · gated_auto/downstream-resolver] Guard's new return value is discarded by every caller  ← **重复**：与已验证的主 finding #12 同源（该视角评为 P2，主 finding 定为 P3）
- **位置**: pcs-backend/app/api/v1/lineage.py:269  ·  pre_existing=False
- **Why**: The diff widened _guard_record_access from '-> None' to '-> Any' and made it return the fetched record, but all three endpoints call it as a bare statement and throw the value away (upstream:70, downstream:116, graph:162). Two costs: (a) the return type is `Any`, a type hole that erases the fact that the value is an ORM row of one of several unrelated model classes — the classic 'leaky abstraction' the schema work in this same diff was trying to fix; (b) _stream_graph then re-fetches the very row the guard already loaded via session.get(Stream, stream_id) (line 284), so the contract is duplicated: the record exists in two places, and the second one is the one that is actually used. A future caller who trusts the returned value and a future caller who trusts session.get can disagree, and the `if stream is None: raise 404` branch inside _stream_graph is unreachable-by-construction (the guard already 404'd) yet is kept alive as a second, differently-worded 404 site.
- **Fix**: Make the contract single: (a) give the guard a precise return type instead of Any — e.g. `-> Base` or a small Protocol exposing the fields the callers need (project_id, pk) — and (b) actually use it: have upstream/downstream/graph bind `record = await _guard_record_access(...)` and pass that row into _stream_graph(session, record, max_depth=...) instead of calling session.get again, deleting the duplicate lookup and the now-unreachable `if stream is None: raise 404` branch. If the returned record is not needed, revert the guard to '-> None' and drop the '## 返回值' docstring section rather than leaving a dead contract in place.

## M3 [P2 · conf 75 · manual/downstream-resolver] current_actor called outside Depends with positional session coupling
- **位置**: pcs-backend/app/api/v1/ws.py:78  ·  pre_existing=False
- **Why**: current_actor is shaped as a FastAPI dependency (Annotated[..., Depends(get_db)]) but the WS path now calls it as a plain function, so the session must be passed positionally as the first argument. The diff itself documents the fragility ('db 排在第一个参数 ... 顺序即调用约定'), which means the parameter order of one route module's helper has become a cross-module contract: any reordering or signature edit in app/api/v1/config.py breaks the WebSocket handshake at runtime, and the only thing signalling that coupling is a docstring. The bigger maintainability cost is that current_actor is now simultaneously three things — JWT decode, role-claim policy, and an account-status DB lookup — and is imported by ~30 other modules from a config router module (app/api/v1/config.py) that has nothing to do with authentication. Adding the DB dependency to this shared primitive is what forced the WS path to open its own session and duplicate the actor-resolution call convention, so there are now two ways to obtain an actor with different session lifetimes.
- **Fix**: Split the shared primitive into a pure part and an I/O part, so the WS path does not have to imitate the dependency: put `decode_actor(authorization) -> _Actor` (JWT + role claim, no DB) in a dedicated module (e.g. app/api/v1/_actor.py or app/core/actor.py) and keep `current_actor` in config.py as a thin Depends wrapper that calls it plus the account-status check. ws.py then calls the pure helper and performs the status check against its own short-lived session, with no positional coupling to a route module's signature. Moving the primitive out of app/api/v1/config.py at the same time removes the ~30-module dependency on a config router.

## M4 [P2 · conf 75 · manual/downstream-resolver] Disabled-account rule implemented twice despite sole-ownership claim
- **位置**: pcs-backend/app/services/user_status_service.py:8  ·  pre_existing=False
- **Why**: The new module's docstring asserts that the disabled-account semantics live in exactly one place in the repository, and the sibling path token_issuer.py contradicts that on the very next login: both encode 'status == DISABLED means deny' with two independent comparisons, one keyed by username (login path) and one keyed by user_id (per-request path). This is the repo's own 'one concept, two definitions' bug family (bug-187~191, cited in the frontend part of this very diff), and the two copies drift for a different reason than the obvious one: the lookup keys differ, so a legacy row whose user_id is not the derived value is judged DISABLED at login but judged 'no row -> allow' on every subsequent request. Adding a third account state (or changing what counts as disabled) requires editing two modules that both claim the rule is theirs. The new module also duplicates the comparison that token_issuer already had, so the diff grew the duplication rather than consolidating it.
- **Fix**: Make the rule single by extracting the comparison, not the query: add to app/services/user_status_service.py a pure predicate such as `def is_disabled_status(status: str | None) -> bool: return status == UserStatus.DISABLED.value`, and have both is_account_disabled and token_issuer.issue_tokens call it. Then correct the docstring: state that the *per-request* semantics are the unique place for the no-row -> allow rule, while the login path deliberately applies the same DISABLED test to the username-keyed row (and say how the legacy-user_id case should behave on each path, or route the login check through the same user_id lookup so the two cannot disagree).

## M5 [P2 · conf 75 · gated_auto/downstream-resolver] Failed set kept in two state slots that drift after clearFailures
- **位置**: pcs-frontend/src/pages/sim/StreamListPage.tsx:449  ·  pre_existing=False
- **Why**: The hook holds the failed items twice: once inside the batch result (result.failed, carrying reason and detail) and once as a bare id list (failedIds). The two are written together on submit but the page reads them from different places: the failure bar and the modal's retry button are gated on failedIds.length, while the modal's failure list, its '失败 N 条' count and its hint text are driven by result.failed. clearFailures() empties only failedIds and leaves result intact, so after the user clicks 清除 the modal still lists the failed streams and still says '关闭弹窗后仍可用上方「只重试失败项」重试这 N 条', but the bar is gone, the modal's own retry button is hidden by the failedIds.length > 0 condition, and retryFailed() is a no-op because failedIds is empty — the hint points at a button that no longer exists and the listed failures can no longer be retried. Two representations of one concept, with the divergence invisible at the call site.
- **Fix**: Keep one source of truth for the failed set. Either (a) have clearFailures also clear the result (setResult(null)) so no stale list or hint remains, or (b) better: stop storing failedIds separately — keep the failed items in a single state slice and derive the ids from it (e.g. `const failed = result?.failed ?? []` plus an explicit 'cleared' flag, or store failedItems in its own slice and derive both the bar count and the retry payload from it). Then gate the modal's list, the retry button and the hint text on the same value so they cannot disagree.

## M6 [P3 · conf 75 · manual/downstream-resolver] Three copies of the record_type == 'streams' branch
- **位置**: pcs-backend/app/api/v1/lineage.py:73  ·  pre_existing=False
- **Why**: The streams special case is now a branch on the same discriminator in three endpoints (upstream:73, downstream:119, graph:165) plus a hand-added 'streams' entry in the guard registry, and each copy encodes a different answer (upstream returns [], downstream queries by source_ref, graph synthesizes a root). Adding a second source-ref style type (or changing how streams should behave) means editing three endpoint bodies plus the registry, and there is no single place that states 'streams is a source reference, not a record type' as executable policy — that fact currently lives in prose across lineage_registry.py, lineage.py's docstrings, schemas/lineage.py and the new schemas. The branching is also a discriminator switch over record_type that a third module would be expected to replicate.
- **Fix**: Resolve the streams case once and let the endpoints stay uniform: put the source-ref logic in the service layer (LineageTracker already owns by_source_ref) and expose a single entry point such as `LineageTracker.for_record_type(record_type).graph(record_id, max_depth)` / `.upstream(...)` / `.downstream(...)`, with the streams-vs-record distinction decided by one dispatch (a small mapping from record_type to strategy) rather than three inline `if` statements. Then the endpoints contain no per-record-type branch at all and a future source-ref type is one mapping entry.

## M7 [P3 · conf 75 · gated_auto/downstream-resolver] Unchecked as StreamSource cast instead of narrowing helper
- **位置**: pcs-frontend/src/pages/sim/tabs/StreamLineageTab.tsx:115  ·  pre_existing=False
- **Why**: The lineage tab looks a value up in STREAM_SOURCE_LABEL by casting it to the StreamSource union: STREAM_SOURCE_LABEL[value as StreamSource]. The cast asserts the value is one of the four channel values when nothing has established that — the value comes from the contract field typed string | null, and text() has already turned a null into the placeholder '—' one line earlier, so the cast is asserting a membership the code cannot know. The repo already has the canonical pattern for exactly this lookup one file over: streamPhaseLabel in src/types/stream.ts, which narrows explicitly and renders '未知相态: X' for out-of-vocabulary values instead of casting. The diff fixed the duplicate label table here (good) but reintroduced a cast on the value, which is the failure mode the shared table was supposed to remove.
- **Fix**: Add a narrowing helper next to the table in src/types/stream.ts, mirroring streamPhaseLabel: e.g. `export function streamSourceLabel(source: string): string | undefined { return (STREAM_SOURCE_LABEL as Record<string, string | undefined>)[source]; }` (or narrow with `source in STREAM_SOURCE_LABEL`), then call it from the tab and drop the `as StreamSource` cast. This keeps the 'unknown value' path explicit and consistent with how the phase vocabulary is already handled.

## M9 [P3 · conf 75 · advisory/downstream-resolver] Reference count exists in two variants with different meanings
- **位置**: pcs-backend/app/services/stream_service.py:344  ·  pre_existing=False
- **Why**: The diff adds reference_counts (downstream streams + flash results, project-scoped) next to the pre-existing _collect_references (state points + flash results, used by the delete gate). Both answer 'does anything reference this stream' and both live in the same class roughly 180 lines apart, but they count different things; the only thing keeping a reader from mixing them up is a paragraph of prose in one docstring and a note in SPEC. This is a duplicated concept with deliberately divergent semantics — legitimate, but the divergence is invisible from the call sites, and the next referencing table added to one of them will silently not appear in the other, which is how the displayed count and the delete gate start disagreeing.
- **Fix**: Make the two scopes explicit in the names rather than only in prose: rename to reference_counts_for_display and _collect_delete_blocking_references (or expose a shared table of referencing sources — e.g. REFERENCE_SOURCES = ((Stream, 'upstream_stream_id', counted=True), (FlashResult, 'stream_id', counted=True), (StreamStatePoint, 'stream_id', counted=False)) — and derive both counters from it so adding a referencing table is a single edit). Keeping the current structure is defensible; the ask is only that the divergence be visible at the call site.

## Residual risks

- reference_count on GET /streams/{id} (single) is always 0 — the field therefore carries two meanings across two endpoints ('no references' vs 'not computed'), even though SPEC documents the caveat. Not reported as a finding because the brief lists it as a registered limitation; flagged here because the field name does not distinguish them.
- assert_mock_auth_not_exposed in app/main.py determines route mounting by calling app.openapi() at startup. That forces full OpenAPI schema generation during lifespan and caches the result, so the schema served later is the startup-time snapshot; the diff's own comment explains why app.routes traversal was abandoned (FastAPI >= 0.141 lazy mounting), but the replacement has a startup cost and a caching side effect that is not discussed in the code.
- The guard registry filters candidates with `hasattr(model, 'project_id')` — duck-typing over ORM class attributes. A model that exposes a relationship or plain attribute named project_id would pass the filter while record.project_id would not be a project id at query time.
- Callsite completeness rests on text search (grep) only: no LSP/AST or symbol-aware search was available in this environment, so statements that a symbol has only one consumer are grep-based and could miss re-exports or dynamic call sites.
- Only the primary backend/frontend source diffs were read; the backend test diff (2225 lines) and the docs diff (5753 lines, mostly ledger and plan text) were sampled rather than read end to end, so a documentation-side contract for the lineage vocabulary may exist that this review did not cross-check.
- No tests were executed and no browser run was performed, so all behavioural statements above (404 shapes, retry semantics, the drift after clearFailures) are derived from reading the diff and the current source, not from observed runs.

## Testing gaps

- No contract test asserts that every model which writes data_lineage rows (i.e. every finalize_calc_record caller) is present in LINEAGE_GUARDED_RECORD_TYPES. Such a test would have failed on PsvResult and is the test that keeps the derived registry from silently drifting.
- No test covers the /lineage/PsvResult/{id}/graph path at all, so the newly fail-closed 404 for a type that genuinely owns lineage rows is invisible to the suite.
- No frontend test exercises clearFailures() while the result modal is open, so the drift between result.failed and failedIds (stale failure list plus a hint pointing at a hidden retry button) is not caught; the existing test only asserts failedIds becomes [].
- No test asserts the guard and the endpoint agree on which stream row is in scope (the guard's select and _stream_graph's session.get), so the duplicated lookup and its now-unreachable 404 branch have no regression cover.
- No test asserts that the WS handshake path and the REST path apply the same disabled-account rule to the same user — the two implementations are keyed differently (username vs user_id), and no test compares their verdicts.
