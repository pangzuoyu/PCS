#### 1. 守门测试会被它所守护的那行注释骗过
- **File**: `docs/solutions/testing-issues/guard-test-fooled-by-lying-comment.md` (2026-10-19, `severity: high`)
- **Module**: pcs-backend + pcs-frontend test validity (`testing_framework`)
- **Problem Type**: `testing_issue`
- **Relevance**: **This diff is the third recurrence of the learning's §5 pattern ("注释比代码乐观"), and it is the one the learning itself warns about — the ledger now records a *false* root cause as fact.** The learning's rule: *"注释里出现「已消除」「唯一来源」「覆盖」这类断言时，把它当成一条待验证的代码事实，而不是既成结论"* and *"凡是「证明 A 引用了 B」的断言，都不该用文本匹配"*.
  - **CHANGED line** `pcs-backend/app/main.py:48-52` (new comment added by this diff) asserts: *"FastAPI ≥ 0.141 改成**懒挂载** ⇒ `include_router` 进来的 router 在 `app.routes` 里是一个**没有 `path` 属性**的包装对象 ⇒ 只遍历 `app.routes` 会**漏掉整棵子树** ⇒ 旧的「生产里 mock 路由不得挂载」断言**一直是空转**（升级后失效了，却一直绿）"*.
  - **Verified false in this repo.** The installed runtime is **FastAPI 0.135.3** (`pcs-backend/pyproject.toml:7` pins only `fastapi>=0.115`, no upper bound). Empirically, `app.include_router(router)` puts a real `APIRoute` with `.path == "/auth/mock-login"` into `app.routes` — so the **old** assertion (`getattr(route, "path", "").endswith("/mock-login")` over `app.routes`) was **not** vacuous; it would have fired. The old assertion was inert for a different reason (`create_app()` never mounts the mock router in production ⇒ nothing to find), which the comment does not say.
  - **CHANGED line** `.wolf/buglog.json` (new entry, `root_cause` field) copies the same claim into the permanent ledger: *"② **部署期断言是空转的** —— FastAPI ≥ 0.141 改成**懒挂载** … ⇒「生产里 mock 路由不得挂载」**升级后失效了，却一直绿**"* ⇒ the wrong cause is now the single source of truth for the next maintainer.
  - **The code change itself is sound** — the OpenAPI-path check is version-independent and strictly stronger than the old route walk, and `test_production_with_mock_route_mounted_fails_startup` (`tests/api/v1/test_mock_auth.py`) does exercise it. The defect is the *rationale*, not the guard. Note the guard test also cannot distinguish old from new implementation (it would have passed against the old code too) ⇒ it pins the *behaviour*, not the claimed mechanism.
- **Key Insight**: "Content equality ≠ derivation; comment ≠ fact." A root cause written into a ledger must itself be verified against the pinned runtime, otherwise the next fix inherits the misdiagnosis.
- **Severity**: high (per frontmatter)

#### 2. 中途配置重绑绕过一次性守卫 —— 审批链必须在提交时冻结（快照）
- **File**: `docs/solutions/security-issues/midflight-config-rebind-defeeds-one-shot-guards.md` (2026-10-31, `severity: high`)
- **Module**: pcs-backend approval chain / authorization (`workflow / authorization`, CWE-863)
- **Problem Type**: `security_issue`
- **Relevance**: Two direct applications inside this diff, one **positive** (the batch avoids the failure shape) and one **residual** (it adopts a fail-open the learning explicitly rejects).
  - **Positive — T0-B is the right shape.** The learning's core rule is *"「一次性检查」守卫的判据源若可变，守卫就是纸"*. The batch moves the account-status check **out** of the one-shot login-time gate (`token_issuer`) into the **actor layer**, re-reading live `users.status` on every request (`pcs-backend/app/services/user_status_service.py:57-58`, called from `pcs-backend/app/api/v1/config.py` `current_actor`). A disable therefore takes effect on the next request rather than only at next login — exactly the "read the mutable source of truth at the point of use" remedy the learning prescribes. The WebSocket path was not forgotten (`app/api/v1/ws.py` `_authenticate` now opens its own session and `await`s `current_actor`), which is the "call site that bypasses the framework" trap this learning warns about.
  - **Residual — fail-open on "no row" (CHANGED, deliberate).** The learning states the opposite rule for the analogous case: *"⚠️ **查不到提交人 ⇒ 响亮 409 `APPROVAL_SUBMITTER_UNKNOWN`，**不放行**「查不到就当没有提交人」（fail-open = 自审绕过）；宁可这条记录卡住等人工处理"*. `is_account_disabled` (`user_status_service.py:57-58`) returns **False** when the `users` row is absent — i.e. **fail-open**. The diff documents the reasoning (ADR-0046 §③b: mock login writes no `users` row; TODO-137 legacy rows), and the reasoning is sound for the mock case, but the **legacy-row case leaks**: a legacy account whose `user_id` ≠ the derived `uuid5(NAMESPACE_DNS, username)` is admitted **even when its `users.status` is `DISABLED`**, because the lookup key (`user_id` from the token) misses the row. Today that window is closed only by the **pre-release manual SQL check** (`SELECT count(*) FROM users WHERE user_id <> uuid5_derived(username)` = 0), not by code. `TODOS.md` registers TODO-137 (migrate legacy authorization) but does **not** register it as *a hole in the disable guarantee*.
  - **Corollary to check in review**: the learning also warns *"前端配套：链信息的**客户端缓存不得跨挂载**"* — the analogue here is the front-end session state for a disabled user (SPEC §7.1 "停用用户的会话"), which should not be allowed to survive a 401 from the actor layer.
- **Key Insight**: A guard whose judgement source can change after the check is paper; conversely, a "cannot determine ⇒ deny" rule must fail **closed**, and any deliberate fail-open must be registered with its residual window.
- **Severity**: high (per frontmatter)

#### 3. SQLite StaticPool 隐藏未提交 —— 测试夹具的观测点盲区
- **File**: `docs/solutions/testing-issues/sqlite-staticpool-hides-uncommitted.md` (2026-10-18, `severity: high`)
- **Module**: pcs-backend test suite — conftest engine fixtures (`testing_framework`)
- **Problem Type**: `testing_issue`
- **Relevance**: **This diff applies the learning correctly — worth recording as a positive.** The learning's rule: *"判据要打在**引擎保证**上（调用序数、对象身份、AST 节点），不要打在**渲染产物**上"* and *"A test that opens a second session to prove a task committed its state passes even when the code only flush()ed — the assertion is void"*.
  - The new WebSocket guard test (`tests/api/v1/test_ws_notifications.py::test_ws_authenticate_rejects_disabled_user`) writes the `DISABLED` user through the fixture session, **explicitly commits** (`await db_session.commit()`), and then points the handshake's own session factory at the **same** `db_engine` (`async_sessionmaker(db_engine, expire_on_commit=False)`) ⇒ the observation point actually sees committed data ⇒ the 1008 assertion is real. The mirrored control test (`..._allows_user_without_users_row`) asserts on the *absence* of a row ⇒ a valid negative.
  - The same discipline appears in the T0-B suite (`tests/api/v1/test_user_disabled_guard.py`): it asserts the **error code** (`USER_DISABLED`), not merely "non-200" (*"只断言状态码的话，「端点炸了返 500」也是非 200"*), and it uses `strict_client` because *"默认 `client` 把项目守卫 mock 成永远 True ⇒ 在它上面「越权被拒」是空断言"* — that is the learning's own false-green taxonomy applied correctly. Same for the T0-C suite, which asserts the **落点 on the DB row** rather than the response body.
  - **Residual note (not a defect)**: `TODOS.md` TODO-141 ("全量测试迁移到 `strict_client`") is still open ⇒ guard assertions written on the default `client` elsewhere in the suite remain vacuous; the new files are the counter-example, not the fix.
- **Key Insight**: Assert on committed, engine-guaranteed state and on error *codes*; a mocked guard makes "denied" assertions void.
- **Severity**: high (per frontmatter)

#### 4. 窄声明不是约束 —— 从局部代码形状推断契约语义
- **File**: `docs/solutions/testing-issues/narrow-declaration-is-not-a-constraint.md` (2026-10-19, `severity: high`)
- **Module**: 前端契约层 + 组件 (`testing_framework` / `contract`)
- **Problem Type**: `testing_issue`
- **Relevance**: **Directly on point for the two "口径" changes in this batch, and the batch handles the hazard correctly in one place while leaving a gap in the other.**
  - The learning's rule: *"inferring_contract_semantics_from_local_code_shape"* and *"看到 X 只有 4 态，就断言…并据此收窄"* — i.e. do not let a locally-visible shape stand in for the real contract.
  - **Handled correctly — the lineage registry (CHANGED).** `app/services/lineage_registry.py` derives `LINEAGE_GUARDED_RECORD_TYPES` from `RECORD_TYPE_REGISTRY` using `model.__name__` (class name), explicitly *not* the registry's own keys, because 5 of those keys are not class names (`cv_result` / `restriction_result` / `flare_system_result` / `cooling_tower_result` / `psychro_result`) ⇒ copying the keys would make those types permanently unfindable. The docstring names the *shape* mismatch explicitly, and `tests/api/v1/...::test_registry_covers_every_writable_record_type` is a **structural mirror test** (iterates the source registry, asserts coverage and asserts the 5 non-class-name keys are *absent*) ⇒ this is the "structural assertion, not text match" the guard-test learning prescribes. Two caveats worth carrying into review: (a) the mirror test pins **coverage**, not **derivation** — if someone later hand-copies the table, the mirror test still passes; (b) the mirror test lives in a lineage test file while the table lives in `app/services/lineage_registry.py` — the AST-based derivation check the learning recommends (`inspect.getsource` + `ast.walk`) is not present.
  - **Gap — the reference-count 口径 (CHANGED).** `app/services/stream_service.py:327` `reference_counts` adds a **same-project filter** (`Stream.project_id == project_id` at :379, `FlashResult.project_id == project_id` at :393) — the Q7 ruling of 2026-11-11 ("只算同项目"), with `project_id` a mandatory keyword-only argument so a forgotten call fails at compile time. **No test creates a second project.** The 8 new tests in `tests/services/test_stream_reference_count.py` all use a single `project` fixture; the one "not over-reach" test (`test_reference_counts_returns_only_requested_ids`) is about the **id set**, not the **project filter**; and the endpoint-level N+1 test only asserts that `project_id` is *passed* (`calls[0][1] == proj.project_id`), not that it is *applied*. The service docstring itself concedes *"今天造不出跨项目引用 … ⇒ 这是**前瞻性保护**，不是修现存 bug"* — precisely the kind of forward-looking rule that silently dies, because the only test that would fail if the predicate were dropped does not exist. This is the same lesson the midflight-rebind entry records under **检测（为什么单测全绿）**: *"钉住它的测试必须**在 submit 之后改配置**再推进一步"* — here, the test must insert a reference row **in another project** and assert it is not counted.
- **Key Insight**: A rule that no test can falsify is a comment; when a new contract is *defined by a local shape* (a registry key set, a count formula), pin it with a structural test and a counter-case.
- **Severity**: high (per frontmatter)

#### 5. `information_schema` 不受 `search_path` 约束 / 方言选项在 SQLite 上隐形（相邻 · 有保留）
- **File**: `docs/solutions/database-issues/information-schema-not-scoped-by-search-path.md` (2026-11-02) and `docs/solutions/database-issues/dialect-options-invisible-on-sqlite.md` (2026-10-18)
- **Module**: pcs-backend data layer — Alembic chain / multi-tenant constraints (`database`)
- **Problem Type**: `database_issue`
- **Relevance**: **Adjacent, with caveats — the batch's own constraints make the primary risk inapplicable, but two residual items survive.**
  - *Not applicable:* the batch changes no `alembic/versions/*` (no drift risk), and the new aggregation uses no dialect-specific options (plain `IN` + `GROUP BY` + `count()`), so the "SQLite is stricter/looser than PG" divergence has no handle here.
  - *Surviving item 1:* the empty-input guard in `reference_counts` (`stream_service.py`, *"**空入参早返回**（`IN ()` 在 PG 上是**语法错误**"*) is correct as written, but note that SQLAlchemy renders an empty `IN` as a false-expression rather than literal `IN ()` ⇒ the stated hazard is slightly off; the early return is still right (and `test_reference_counts_with_empty_input_returns_empty_dict` pins it).
  - *Surviving item 2:* every new test in this batch runs on the in-memory SQLite harness (`sqlite+aiosqlite:///:memory:` + `SA_Base.metadata.create_all`) ⇒ per the learning, the test schema is a **rendering of the ORM** and therefore agrees with the ORM by definition ⇒ a green suite is not evidence about PG. The two aggregate queries are exercised only on SQLite; there is no `pg`-marked engine-level test for them. `scripts/pytest_pg.sh` remains the only real-PG lane. Caveat: no PG-specific SQL is involved, so the risk here is **low** — but the *same* is true of the cross-project filter, which is why item 4 above matters more.
- **Key Insight**: "Green on SQLite" is a statement about the ORM's rendering of itself, not about the deployed database.
- **Severity**: medium (per frontmatter)

### Recommendations

- **Fix the recorded root cause before it becomes folklore.** Rewrite the `pcs-backend/app/main.py:48-52` comment and the `.wolf/buglog.json` `root_cause` for the mock-auth entry to state the *actual* reason the old assertion never fired (`create_app()` does not mount the mock router in production ⇒ nothing to find), and state the OpenAPI-path check as *version-independent hardening* rather than as a repair of a vacuous guard. Keep the code change — it is correct and stronger. If the FastAPI ≥ 0.141 lazy-mounting behaviour is real, it belongs in a comment as a *future* risk with the pinned version named, not as the cause of a bug that never happened here.
- **Add the one missing test: a cross-project reference must not be counted.** Create a second project in `tests/services/test_stream_reference_count.py`, insert a downstream stream / flash result whose `project_id` differs from the queried one (direct ORM insert, since the service layer currently prevents it), and assert `counts[...] == 0`. Without it, the Q7 same-project rule is enforced by two SQL predicates that no test can falsify — exactly the "前瞻性保护 dies silently" shape.
- **Do not treat the "no `users` row ⇒ allow" decision as settled.** It is a deliberate, documented fail-open that contradicts the repo's own fail-closed precedent. Either (a) register the residual explicitly in `TODOS.md` — "a legacy row with `user_id` ≠ the derived id is admitted even when `DISABLED`; closed only by the pre-release SQL check" — or (b) close it in code by keying the lookup on `username` (the token's `sub`), which is stable across the TODO-137 migration. Right now the guarantee "停用立即生效" holds only for rows whose id matches the derivation rule.
- **Pin derivation, not just coverage, for the lineage registry.** The mirror test proves every writable type is registered, but a future hand-copy of the table would still pass it. Add the AST-based derivation check the guard-test learning prescribes (`inspect.getsource` + `ast.walk` for a `RECORD_TYPE_REGISTRY` reference) in `app/services/lineage_registry.py`'s own test file, so "派生" is a testable fact rather than a comment.
- **Fold the lineage read path into the same-project rule, or say why not.** `LineageTracker.by_source_ref` (`app/services/lineage.py:144`) filters only on `source_ref_type`/`source_ref_id` — **no `project_id` predicate** — while the sibling count column was just given one (Q7). `finalize_calc_record` (`app/services/calc_lineage.py:237`) does not itself enforce that the source streams belong to the record's project. Caveat: I found no code path that actually creates such a cross-project reference today (`create_outlet_stream` forces `source.project_id == project_id`; `flash_persist` uses `stream.project_id`), so this is a consistency/hardening item rather than a demonstrated defect — but the two endpoints currently apply the same rule differently, and the batch's own Q7 ruling is the natural place to reconcile them.
- **One-line mock note (low priority).** `pcs-frontend/src/mocks/seed/streams.ts` now hardcodes `reference_count` values (2/0/1/0/3) that correspond to no mock relationship, and the mock single-stream endpoint therefore reports a non-zero count where the backend's `GET /streams/{id}` returns 0 (a documented limitation of this batch). The *shape* is safe — `Stream` is the generated `components['schemas']['StreamResponse']`, so `tsc` catches field drift — but per the mock-drift learning, "mock 与契约一致是正确性的一部分", and a future page that reads `reference_count` on the detail view would be green in dev and wrong in production.
