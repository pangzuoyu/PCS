# ADR-P8-004：报表任务队列隔离与文件生命周期

状态：**待运维确认**（2026-10-08 用户裁决：需要运维输入，不在开发侧拍板）
日期：2026-10-08
决策者：**运维 + 架构**
关联：ADR-P8-001（全直接生成模式）、实施计划 `docs/superpowers/plans/2026-10-08-p8-report-and-report-builder.md` Task 6 / Task 7

## 背景

P8 引入两类与既有 P7 任务**资源特征完全不同**的负载：

| 负载 | 资源特征 | 现有归属 |
|---|---|---|
| 报表生成（ReportLab / XlsxWriter） | **CPU 密集**，单任务 1–5s，复杂报表 1–3s（PDF） | 新增 |
| workspace 清理、stale 扫描 | IO + 数据库，轻量 | 已有（`app/workers/worker.py`） |

当前 `WorkerSettings.max_jobs = 4`，两类任务**共用同一个 worker 进程与同一队列**。
SPEC §3.3.1 的性能预算（简单 ≤5s / 复杂 ≤15s）在这条链路上没有保障。

同时，P8 产出的是**落盘文件**（PDF/XLSX/DOCX），而 `report_files.project_id` 带
`ondelete="CASCADE"`。项目删除后 DB 行没了，**磁盘文件留下** —— 长期运行产生孤儿文件。

---

## 待决事项

### 决策 1：队列隔离方式

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 单队列 + 提高 `max_jobs`** | 报表与清理任务同进程，靠并发数调节 | 报表 CPU 密集会抢占清理任务 → 清理饿死 → 磁盘满；清理长跑会拖慢报表 |
| **B. 双队列 + 双 worker 进程** | `arq report.worker` 与 `arq main.worker` 分开部署 | 需两套进程管理；内存占用翻倍 |
| **C. 单进程 + 优先级** | ARQ 的 queue 参数 + 报表任务高优先级 | ARQ 的优先级支持有限；仍共用 worker 槽位，CPU 争抢无隔离 |

**倾向 B**，但需运维给出部署形态（K8s Deployment？systemd？docker-compose？）。

**需运维确认的输入**：
1. 生产环境怎么起 ARQ worker（当前仓库无 worker 的部署配置，只有 `docker-compose.yml` 给服务本身）
2. 报表并发的业务上限（同时有几个用户在生成报表）
3. 目标机器的 CPU 核数 —— `max_jobs` 应设多少

### 决策 2：文件保留策略

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 永久保留** | 永不删除 | 磁盘单调增长，无上界 |
| **B. 随项目级联删除** | 项目删 → 文件删（需 ARQ 定时任务扫孤儿） | 需清理任务 + 失败重试（TODO-016 记「ARQ 失败路径覆盖为零」） |
| **C. 固定 TTL** | 生成后 N 天过期 | 需产品定 N；正式计算书可能需要长期存档 |
| **D. 只增不减 + 磁盘配额告警** | 不清理，监控磁盘 | 最简单，但磁盘打满时服务不可用 |

**倾向 B + D 组合**：孤儿文件清掉，同时对磁盘设阈值告警（兜底）。

**需运维确认的输入**：
1. 报表文件存储的卷容量与增长预期
2. 是否有既有的磁盘监控告警通道可复用
3. 清理任务的执行频率（ARQ cron 已在 `worker.py` 有先例）

---

## 与其他决策的关系

- **决策 2 的 B 方案依赖 TODO-016**（ARQ 失败路径零覆盖）。清理任务失败必须
  有重试与告警，否则会变成「静默不清理」。这一点应与 TODO-016 一并解决。
- **决策 1 不影响 SPEC 性能预算**——预算约束的是单次生成耗时，不约束并发。
  但并发不足会让用户感知为「一直转圈」。

---

## 在此 ADR 确认前

实施计划的 Task 6 / Task 7 按**方案 A（最简）** 实现：
- 报表任务与既有任务同队列，`max_jobs` 暂不调整（保持 4）
- 文件**不清理**（只增不减）

并在 Global Constraints 明确标注这是临时状态，运维确认后回改。
**不得在未确认的情况下自行实现清理任务** —— 删错文件不可逆。
