## 背景

P8 引入两类与既有 P7 任务**资源特征完全不同**的负载：

| 负载 | 资源特征 | 现有归属 |
|---|---|---|
| 报表生成（ReportLab / XlsxWriter） | **CPU 密集**，1 ms/行，10k 行 PDF ≈ **9.6 CPU-秒** | 新增 |
| workspace 清理、stale 扫描 | IO + 数据库，秒级 | 已有（`app/workers/worker.py`） |

当前 `WorkerSettings`：`max_jobs = 4`、`job_timeout = 300`、**未设 `max_tries`**
（即 ARQ 默认 5）、cron 每 1 分钟增量 / 每 5 分钟全量。两类负载**共用同一进程与同一队列**。

### 实测数据（本机 20 核，2026-10-12）

| 行数 | PDF | XLSX |
|---|---|---|
| 1 000 | 0.50 s / 80 KB | 0.02 s / 25 KB |
| 5 000 | 3.46 s | — |
| 10 000 | **9.56 s / 673 KB** | 0.23 s / 201 KB |

三条结论：

1. **PDF 线性于行数**（≈1 ms/行，跨 10× 行数无超线性爆炸）。
2. **XLSX 比 PDF 快约 40 倍** —— 大报表优先走 XLSX 是最有效的性能手段，
   比任何并发调优都划算。
3. **一份 10k 行 PDF ≈ 10 CPU-秒**。`max_jobs = 4` 意味着最坏情况下
   4 个 PDF 并发会吃满 4 个核；在 2 核机器上，一个报表就占满全部算力。

### ⚠️ 初版背景有一处已失效，务必注意

初版写「`report_files.project_id` 带 `ondelete="CASCADE"`，项目删除后 DB 行没了、
磁盘文件留下 → 孤儿文件」。

**这在 Task 2 之后已不成立**：`report_files` 上 **0 个 FK**
（实测 `pg_constraint` 确认，`app/models/report.py` 刻意不加）。
项目删除后 `report_files` 行**保留** —— 这正是设计意图：有记录才谈得上清理。

所以本 ADR 要解决的问题**不是**「孤儿文件」，而是「**所有文件都该留多久**」。

### 内容指纹复用（bug-155 修复后）

文件按内容指纹命名（`{hash[:16]}.{ext}`），同内容重复生成**复用同一行同一文件**。
注意指纹是对**规范化内容**取的（不是渲染字节 —— PDF 字节每次都不同，
reportlab 随机 `/ID`），所以重复生成同一份报表**不会**新增文件或行。

## 决策 1：队列隔离

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 单队列 + 提高 `max_jobs`** | 报表与清理同进程，靠并发数调节 | 报表 CPU 密集会抢占清理任务 → 清理饿死 → 磁盘满；反之清理长跑拖慢报表 |
| **B. 双队列 + 双 worker 进程** | ARQ 按 `queue_name` 天然支持多队列；新增 `ReportWorkerSettings` | 需两套进程管理 |
| **C. 单进程 + 优先级** | ARQ 无真正的优先级；仍共用 worker 槽位，CPU 争抢无隔离 | 不解决 CPU 争抢 |

**建议 B**，理由是 A/C 都只在**调度层**打补丁，而两类负载的争抢发生在
**CPU 层**。`queue_name` 是 ARQ 的一等参数，B 只需新增一个约 20 行的
`ReportWorkerSettings`（不同 `queue_name` + 独立 `max_jobs`），可逆、低风险。

**建议 `max_jobs`：报表 worker 设 2**（保守）。依据：一份 10k PDF ≈ 10 CPU-秒，
2 并发在 4 核机器上是 50% 占用，再高会让清理 worker 拿不到核。
最终值取决于运维给的核数。

⚠️ **但本决策目前无法落地**：仓库的 `docker-compose.yml` 只有
postgres / redis / openldap / openldap-seed **四个服务，没有 backend、
没有 worker**；CI 也没有任何 `arq` 步骤。也就是说**目前没有任何部署配置**，
「生产怎么起 worker」在仓库里无处可查。这个缺口比队列选型更值得先补。

## 决策 2：文件保留策略

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 永久保留** | 永不删除 | 磁盘单调增长，无上界 |
| **B. 随项目级联删除** | 项目删 → 文件删 | ⚠️ 前提已失效（`report_files` 无 FK，行不会被级联删）。且**对外交付的计算书可能需要长期存档** —— 删了不可逆 |
| **C. 固定 TTL** | 生成后 N 天过期 | 需产品定 N |
| **D. 只增不减 + 磁盘配额告警** | 不清理，只监控 | 最简单，但磁盘打满时服务不可用 |

**建议 C + D 组合**，TTL 默认 **180 天**（可配置，`report_retention_days`），
同时对存储卷设阈值告警兜底。

理由：

- **B 不再成立**（无 FK，行不会被级联删），且报表可能是**对外交付的计算书**，
  随项目删文件是不可逆的错删。
- **A 无上界**，且内容指纹复用只解决「重复生成」，不解决「数据变了生成新版本」
  —— 每次上游数据变动都会产生新指纹。
- **C 的 N 需要产品确认**，180 天是我按「工作稿 vs 交付件」的经验值，
  不是行业标准。**这一条要产品拍，架构侧不代拍。**
- **D 是必须项而非可选项**：TTL 任务本身也会失败（TODO-016：ARQ 失败路径
  覆盖为零），没有告警的话「静默不清理」与「永久保留」没有区别。

**清理任务删除什么**：同时删 `report_files` 行与磁盘文件。⚠️ 顺序必须是
「先删文件、成功后再删行」—— 反过来会留下「行在但文件没了」的记录，
比孤儿文件更难排查（用户点下载得到 404，还以为文件被篡改）。

## 决策 3：行数上限与超时

SPEC §3.2.2(2) 的 `MaxRows` 默认 10000。实测 **10k 行 PDF ≈ 9.6 s**，
而 SPEC §3.3.1 的预算是「简单 ≤5 s / 复杂 ≤15 s」。也就是说
**默认配置下最大报表已经把简单档预算用掉两倍**。

**建议**：

1. `max_rows` 上限保持 10000（SPEC 值），但**在 UI 上对 >5000 行的导出
   提示「建议改用 Excel」** —— XLSX 快 40 倍，用户体验差异巨大。
2. 报表 worker 显式设 `job_timeout = 60`（10k PDF 约 10 s，60 s 有 6 倍余量；
   沿用全局 300 太宽，真卡死的任务会占着槽位 5 分钟）。
3. **显式设 `max_tries`**（当前未设 = ARQ 默认 5）。见下节。

## 与用户 2026-10-09「ARQ 重试审计模型」裁决的衔接

用户已裁决：**每次失败都写一条 `REPORT_FAILED`，`detail_json` 带
`{"task_id", "attempt_no"}`；`REPORT_GENERATED` 只在最终成功时写一次。**

这条裁决与本 ADR 的队列决策有直接耦合，且比队列选型更要紧：

ARQ 的 `keep_result` 默认 **3600 秒** —— 任务结果与异常在 Redis 里
**1 小时后被清除**。也就是说 **Redis 不是失败的持久记录**，
`audit_logs` 是唯一一份。裁决「每次失败都写一条」因此不是可选的审计偏好，
而是**失败可追溯性的唯一保障**。

由此产生三条硬性实现约束：

1. `max_tries` 必须**显式设置**，并在 `detail_json` 里记 `attempt_no`
   —— 默认 5 次意味着一次失败可能产生 5 条审计行，这是**预期的**，
   「重试过几次」本身就是有价值的信号（某类报表平均重试 2 次 = 有系统性质量问题）。
2. 重试耗尽后必须有一条**终结状态**：建议在 `report_files.status` 记 `FAILED`
   并保留 `error_message`，否则前端只能看到「转圈到超时」。
3. **TODO-016（ARQ 失败注入 + DLQ 覆盖为零）应在 T7 落地时一并解决** ——
   在失败路径零覆盖的前提下上线重试逻辑，等于上线一段没人测过的代码。

## 在本 ADR 确认前

实施计划的 Task 7 按**临时方案**实现，不阻塞其余任务：

- 报表任务与既有任务**同队列**，`max_jobs` 保持 4
- 文件**不清理**（只增不减），但**内容指纹复用已生效**，重复生成不膨胀
- **不得在未确认的情况下自行实现清理任务** —— 删错文件不可逆

**这些临时状态在确认后回改的成本很低**：队列隔离只需新增一个
`ReportWorkerSettings` 并改启动命令；TTL 只需加一个 cron + 一个配置项。
两者都是**加法**，不是重构。
