# P9-Prep MFA 决议备忘

- **日期**：2026-10-19
- **关闭**：SPEC §8 的 `P9-OPEN-001` / `P9-OPEN-002` / `P9-OPEN-004` / `P9-OPEN-006`
- **拍板人**：PCS 架构组（单人开发，用户裁决）
- **关联**：ADR-0007（客户凭证代录）、ADR-0046（用户身份模型）、
  `spec/PCS-REQ-2026-002-SPEC-P9 …（修订版）` §2.2.4

---

## 1. 为什么这是硬阻塞

SPEC R7 把 `P9-OPEN-001`（MFA）从「待确认」升级为硬阻塞，依据是**两条核心链路都依赖它**：

- SPEC §3.2.1 的「通过 / 退回」操作
- SPEC §3.2.1(5b) 的代录客户批准

ADR-0007 原文（`docs/adr/0007-customer-approval-proxy-recording.md:10`）：
「代录人**二次认证（AD 密码/MFA）**」。这条约束在 P0/P1 就写死了，
代录链路的其它部分（凭证附件 SHA-256、客户批准人姓名/日期/方式、
代录人不得是该交付物设计人）都已就位或已有归属，**只差这一项没有实现依据**。

现状实测：`grep -rn "CUSTOMER_APPROVAL_PROXIED|SIGN_2FA" app/`
只命中 `app/models/enums.py:377` 的枚举定义本身 ——
**没有二次认证的实现，没有 `verify_secondary_auth()` 这个函数**。

---

## 2. 两条路径对照

| 维度 | 路径 A：真 MFA（TOTP / 短信 / 硬件令牌） | 路径 B：Fallback（AD 密码二次输入） |
|---|---|---|
| 外部依赖 | 公司已有 MFA 服务，或需采购 + 发放流程 | 无 —— 复用既有 LDAP 通道 |
| 与 ADR-0046 的关系 | 独立（不依赖 users 表） | 复用二次输入入口，需与 §③ 的停用判定协同 |
| 代录场景（ADR-0007） | 需在 `customer-approval/proxy` 内嵌 TOTP 校验 | 复用 LDAP 再认证 |
| 审计 action | `SIGN_2FA_OK` | **`SIGN_2FA_FALLBACK`** |
| 失败处理 | 校验失败拒签 | 校验失败拒签 |
| 实施成本 | 高（采购 / 接入 / 前端 enrollment） | 低（一次再认证调用） |
| 后续替换成本 | — | 需二次改造代录链路 |
| mock 下的二次认证 | 不适用（mock 本就不做二次认证） | 已裁决豁免，见 §4 |

**路径 B 的技术基础已核实**：`app/services/ldap_client.py:58` 已有
`authenticate(username, password) -> LdapUser`（LDAP bind），
代录人二次输入直接复用它，**不新增凭据通道**。

---

## 3. 裁决：路径 B —— AD 密码二次输入 + 强制审计

**P9-OPEN-001 关闭。** 落地约束四条：

1. **审计 action = `SIGN_2FA_FALLBACK`**（SPEC §2.2.4 路径 B 指定名），
   写入 `audit_logs`。**不得**复用 `SIGN_2FA_OK` ——
   后者会掩盖「我们没上真 MFA」这个事实，使日后审计读不出当前用的是降级方案。
2. **二次输入验证的是操作者本人的 AD 密码**，走既有
   `authenticate(username, password)`（`app/services/ldap_client.py:58`）。
3. **路径 B 是明确的过渡态，不是终态。** SPEC §2.2.4 原文即「MFA 后续替换」。
   替换时应新增 `SIGN_2FA_OK` 与真 MFA 校验，届时 `SIGN_2FA_FALLBACK` 转为历史值。
   **不得**在 Fallback 路径上直接改用 `SIGN_2FA_OK` 冒充已上 MFA。
4. **mock 会话豁免**（见 §4）。豁免范围限定在登录层，
   `verify_secondary_auth()` 函数本身不得豁免。

### P9A 交接

P9A-DLV-008（代录客户批准后端）需新增：

- `SIGN_2FA_FALLBACK` 审计枚举
- 二次认证中间件（基于 `ldap_client.authenticate`）

SPEC §3.2.1 的通过/退回两条链路与 §3.2.1(5b) 代录批准都依赖它 ——
这正是 SPEC R7 把它升级为硬阻塞的理由。

---

## 4. 裁决：mock 用户豁免二次认证

`/auth/mock-login` 不查 LDAP，只查硬编码 `MOCK_USERS`
（`app/api/v1/mock_auth.py:14-19`），mock 用户**没有 AD 密码** ——
路径 B 的「AD 密码二次输入」在 mock 下本就无密码可输。

### 为什么这个豁免是安全的

不是「测试环境有豁免、生产没有」那种危险形态，理由是可核实的：

```python
# app/main.py:118-119
if not settings.is_production:
    app.include_router(mock_auth_router)
```

**mock 路由在生产环境根本不存在**（`mock_auth.py:53-56` 里还有第二道
`if get_settings().is_production: raise` 双重保险）。
mock 会话在生产上无法产生，所以「豁免」**没有生产面可绕**，
不构成绕过二次认证的后门。

### ⚠️ 豁免范围必须限定在登录层

| | 豁免 | 不豁免 |
|---|---|---|
| mock 会话**触发**二次认证 | ✅ 豁免（本裁决） | — |
| `verify_secondary_auth()` 函数本身 | — | ❌ **不得豁免** |

豁免只发生在「谁来登录」这一层。二次认证的**实现**照常存在、照常被要求。
因此 P9A-DLV-008 **必须**对二次认证函数做**直接单测**，绕开 mock 登录路径 ——
否则 mock 全绿会被读成「二次认证验证过了」，而它其实没跑过。

### 残留风险（写明，不掩盖）

dev / QA / pytest 环境**永远**测不到「真实用户走完整二次认证流程」这条端到端链路。
该链路的验证责任落在 P9A 的集成环境（需真 LDAP），不属于 mock 覆盖面。
**P9A 的测试计划须写明这一条。**

## 5. 裁决：P9-OPEN-002 —— 本版不设邮件服务器，预留接口

邮件作为**下一版功能**，本开发版不实现投递。落地约束三条：

1. **本版通知主通道 = 站内信**（铃铛 + 待办列表）。与 SPEC §3.1.1 的 UI 描述一致
   （「通知中心：顶部铃铛图标，下拉展示通知列表」），且 §3.1.1 待办列表本就
   「登录后首页展示」—— 站内信在登录模型下自洽，无需邮件补位。
2. **预留通道接口，不预留具体实现。** P9A 的通知写侧须经一个通道抽象
   （`NotificationChannel` 协议 + `InAppChannel` 实现），邮件作为其未来的一个实现，
   **本版不写** `EmailChannel`。**不写空壳实现** —— 空壳会假装有邮件通道已就绪，
   下一版接的时候才发现接口签名不对。
   **不得**在 service 里直接 `if 走邮件: ...`，那会让「预留」变成「临时 if」。
3. **用户不可达时无处可达。** 站内信只在用户登录时可见；离线用户不会收到任何
   主动提醒，直到他自己登录为止。开发版可接受；正式版上此行为前**必须**有邮件或推送通道。

### 连带影响

| 影响面 | 变化 |
|---|---|
| ADR-0049 §① | 通知写侧异步的**理由变了** —— 原理由是「不阻塞外部投递」，本版**没有外部投递**，异步只剩「不阻塞写库」。ADR-0049 已据此改写为「不锁，留待 P9A 按实际压力决定」 |
| P9A-NOT-004（30 天清理） | **不变**。清理是本地定时任务，与有无邮件无关 |
| P9-OPEN-006 | **权重上升**。去掉邮件后实时推送成了通知唯一的及时性来源 ⇒ 从「建议」升为**明确确认** |
| ADR-0007（代录二次认证） | 不受影响（走 AD 密码，不走邮件） |

## 6. 裁决：P9-OPEN-004 / P9-OPEN-006

| 编号 | 裁决 | 依据 |
|---|---|---|
| P9-OPEN-004 用户同步定时频率 | **每日凌晨** | 沿用 SPEC 倾向，无新增依据 |
| P9-OPEN-006 通知推送方式 | **WebSocket + 降级轮询** | 沿用 SPEC 倾向；且因邮件已移除（§5），实时推送成为通知唯一及时性来源 ⇒ 从「建议」升为**明确确认** |

**P9-OPEN-006 的连带要求**：WebSocket 是本版通知体验的**关键路径**，不是可选增强。
断线时降级到轮询；**不得**在 WebSocket 不可用时直接停止推送 ——
那等于通知静默失效，而通知系统失效无声正是 ADR-0047 立观测层要防的那类问题。
降级状态应**可观测**（健康端点或指标），不能只靠前端感觉。

## 7. 两条路径都无法回避的事实

SPEC §3.2.1 的「通过 / 退回操作」与 §3.2.1(5b) 的代录批准**两条链路都依赖**二次认证 ——
这才是 SPEC R7 把它升级为硬阻塞的理由，与选哪条路径无关。
换句话说：**即使将来切到路径 A，这两条链路仍然需要二次认证，只是实现不同。**
本次决议不解除这个依赖，只确定了实现方式与审计口径。
