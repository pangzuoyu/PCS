## ① §3.4 约束② 冲突 —— 文档修订

**冲突双方**（技术上不矛盾，意图上需一次统一）：

| | 本项目「注释不是契约」裁决 | 本体论 §3.4 约束② |
|---|---|---|
| 对象 | ORM comment ↔ PG `COMMENT ON` | ORM comment ↔ Pydantic `Field(description=...)` |
| 主张 | 注释不影响运行时 / 门禁 / API 契约 | 两个描述文本之间要一致，漂移即 fail |

**裁决：选项 a** —— 把 §3.4 约束② 的对比链**限定在「ORM comment ↔ Pydantic
description」这条描述文本链上，去掉对 PG `COMMENT ON` 路径的依赖**。

**理由**：描述文本的单一事实来源是正当意图 —— 读代码的人看 ORM comment，读 API 的
人看 Pydantic description，两者不一致会误导读者。但这条链**不该经过 PG**：
`COMMENT ON` 是 alembic 管辖的 schema 元数据，与「描述文本」无关。

两者可以并存：今天关掉的是「注释 → 系统行为」的耦合，§3.4 管的是
「代码注释 → 文档文本」的一致性。前者不阻止后者存在。

**修订后的 §3.4 约束②**（取代原文）：

> 对比链限定在 ORM column comment ↔ Pydantic `Field(description=...)` 之间，
> **不经 PG `COMMENT ON` 路径**（后者由 alembic 管辖，与描述文本无关）。
> 意图不变：描述文本单一事实来源 —— Pydantic Schema 是 JSONB 子结构的唯一载体，
> ORM comment 需与之一致但非主源。

### 🔍 复核后的两处更正（2026-10-07 实测原文）

**其一：约束② 原文本来就只涉及 ORM ↔ Pydantic，从未提 PG `COMMENT ON`。**
原文为「P4 Task 0-Code 起加 ORM Column comment ↔ Pydantic Field description 静态
对比 CI 测试（漂移即 fail）」。所以本条**实质是澄清而非改动** —— 两条裁决从来不在
描述同一种关系，本就不冲突。此前把它们并列为「冲突」讲重了。

**其二：约束② 要求的检查根本不存在。** 原文要求「CI 测试（漂移即 fail）」，但
- `pcs-backend/scripts/` 下**无任何** comment / description 对比脚本
- 唯一的 workflow（`.github/workflows/check-api-drift.yml`）只跑
  alembic upgrade / OpenAPI 导出 / API drift / 迁移幂等闸 / 前端 typecheck，
  **不含该对比**

即约束② 自 P4 Task 0-Code 起就是**纸面要求，从未落地**。P8 要用它生成报表元数据，
前提是描述文本可信 —— 而可信度当前没有任何机制保障。

⚠️ **落地前需先定义该对比的契约**（原文未说清）：`*_result` 表的 JSONB 载荷存在
单列里，ORM 该列的 comment 究竟对应 Pydantic 模型的**哪个字段**的 description？
顶层字段？全部子字段拼接？未定义清楚就写脚本，必然写出一堆假阳性。

**约束③「P8 前评审现有 JSONB 字段的 Pydantic Schema 覆盖情况」同样未执行。**

## ③ F-P3-001 JWT issuer —— 不是代码没写，是部署前置没配

Sprint 3 的裁决是 **config-driven 对称**，代码是对的：未配置就不写不校，
配置了就写就校。ce-code-review 的「P8 前置」真实含义是
**生产环境必须配置 `PCS_JWT_ISSUER` / `PCS_JWT_AUDIENCE`**。

**不该用代码硬编码默认值解决** —— 那会破坏 config-driven 语义。
**真实动作是 fail-fast**：生产启动时若 `is_production=True` 但
`jwt_issuer` / `jwt_audience` 未配置 → 启动失败。

```python
# app/core/config.py
@model_validator(mode="after")
def _jwt_iss_aud_required_in_production(self):
    if self.is_production and (not self.jwt_issuer or not self.jwt_audience):
        raise ValueError(
            "PCS_JWT_ISSUER / PCS_JWT_AUDIENCE 必须在生产环境配置。"
            "未配置 = PyJWT 静默跳过校验 = 生产无 issuer 防护。"
        )
    return self
```

约 5 行代码 + 1 条测试。比「给 `jwt_issuer` 补默认值」更 boring ——
它保留了 config-driven 对称，只是加一道「生产必须配」的门。**~0.1 人天。**

## ④ P8 spec 措辞修订 —— 把「能力」误写成「数据」

P8 spec §2.6 原文：**「依赖 P7：EQUIP_LIST 等数据表已填充数据。」**

问题：P7 交付的是**录入能力**（`record_actual_data` / `confirm_actual_data` + API），
真实数据不存在（没有真实项目的设备录入过）。spec 把能力当成了数据。

**修订为**：

> 依赖 P7：EQUIP_LIST 等数据表的**录入能力**已交付（表 + API）。
> P8 测试需自备数据种子（seed 脚本或 fixture），**不假设真库有数据**。

**P8 内部工作随之新增**：写 seed 脚本（~0.5 人天），属 P8 内而非前置。

## ② 的执行结果：读面已做，写面改判到 P9（2026-10-07）

**读面一次做完**（`23c8c25`）：`GET /deliverables`、`/{id}`、`/{id}/versions`、
`/{id}/versions/{rev}/snapshot`。**P8 REPORT 的实际数据依赖已打通** —— 本项设立时
给的三条理由里，有两条本质是「读」（REPORT 从 `deliverables`/`deliverable_versions`
取数据、引用变更历史），只有第三条（手动触发 REPORT 的 UI）沾写。

**写面改判到 P9**，理由：
1. P1 spec 给它们的语境是**签署流程** —— `issue` = 选版本目的→生成 Rev→走签署矩阵；
   `proxy` = ADR-0007 代录客户批准（凭证附件 + 二次认证）。那是 P9 的范围。
2. 三者都依赖签署矩阵消费方，而 `SignatureMatrix.steps_json` **目前无 service**
   （SUP-005 未落地）。
3. 现在强行做，等于在没有矩阵语义的情况下把签署流程写死一遍，P9 开工时必推翻。

**顺带查出 bug-145**：`ChangeNoticeService.create_change_notice:191` 写死
`matrix_id=None`，但 `Deliverable.matrix_id` 是 **NOT NULL 带 FK** —— 该路径
**调用即 500**。无任何测试、真库表 0 行，所以从未爆。修法两条：先建矩阵消费方
（P9 范围），或放宽列可空（丢引用完整性、与「无矩阵就无法签署」的设计意图相悖）。
**倾向前者。**
